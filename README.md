# BrokerReport

Анализ брокерских отчётов (HTML/XLSX) с веб-интерфейсом, SQLite и Docker.

## Быстрый старт (локальный)

```powershell
# Установка зависимостей
pip install flask beautifulsoup4 lxml firebase-admin pandas openpyxl

# Запуск (без авторизации устройств)
python run.py
```

Откройте http://127.0.0.1:5000

## Быстрый старт (Docker)

```bash
# Сборка и запуск
docker compose up -d

# Просмотр логов
docker compose logs -f
```

Откройте http://localhost:5000

> **При первом запуске:** авторизация устройств включена автоматически.
> Используйте админ-панель `/admin` с токеном `admin123` (или смените его в `docker-compose.yml`).

## Как это работает

1. HTML-отчёты брокера кладутся в папку `reports/`
2. При запуске скрипт автоматически импортирует все `.html`/`.HTML`/`.xlsx` файлы в SQLite
3. Фоновый дозор раз в минуту проверяет новые файлы
4. На дашборде — прибыль/убыток по трейд-сделкам (LIFO), открытые позиции, расходы на РЕПО
5. Фильтр по датам позволяет выбирать период для анализа
6. **Авторизация устройств** — администратор управляет доступом (см. ниже)
7. **Репликация БД в Firebase Realtime Database** (опционально)

## Авторизация устройств

Система позволяет администратору управлять доступом к данным (страницы и API).

### Концепция

- **Device ID** — уникальный идентификатор устройства (генерируется браузером или задаётся вручную)

## Скринер акций (объёмный анализ)

Страница `/screener` — скринер по **обезличенным сделкам** MOEX из T-Invest API
(Т-Банк). Идея: по ленте всех сделок оценивать, кто в бумаге доминирует —
покупатели или продавцы.

### Как включить

1. Получите токен в личном кабинете T-Invest (нужен только доступ к
   котировкам — «только чтение»).
2. Добавьте в `.env`:

```bash
TINKOFF_TOKEN=t.xxxxxxxxxxxxxxxxxxxxxxxxx
```

3. Перезапустите приложение — фоновый сборщик запустится сам.

Без токена страница открывается, но показывает предупреждение и пустую таблицу.

#### Сертификат T-Invest и TLS

`invest-public-api.tinkoff.ru` отдаёт сертификат **УЦ Минцифры**
(Russian Trusted Sub CA). В наборе `certifi` этого корня нет, поэтому «из
коробки» Python падает с `CERTIFICATE_VERIFY_FAILED`, хотя браузер и `curl`
работают (они используют системное хранилище).

Проверку сертификата приложение **никогда не отключает**. Источники доверия:

1. пакет `truststore` (есть в `requirements.txt`) — берёт корни из хранилища ОС,
   поэтому на macOS и на сервере с установленным сертификатом Минцифры всё
   работает без настроек;
2. `TINKOFF_CA_BUNDLE=/path/to/ca.pem` — дополнительный корневой сертификат
   поверх `certifi` (нужен, если корня Минцифры в системе нет).

Если в контейнере сертификата нет, положите PEM в `secrets/` и пропишите путь
внутри контейнера:

```bash
# macOS: выгрузить корневые сертификаты из связки ключей
security find-certificate -a -p /Library/Keychains/System.keychain > secrets/tinkoff-ca.pem

# .env
TINKOFF_CA_BUNDLE=/app/secrets/tinkoff-ca.pem
```

```yaml
# docker-compose.server.yml, в секцию volumes сервиса broker-report
- ./secrets/tinkoff-ca.pem:/app/secrets/tinkoff-ca.pem:ro
```

На Linux-сервере тот же PEM можно поставить в систему и обойтись без переменной:

```bash
sudo cp tinkoff-ca.pem /usr/local/share/ca-certificates/tinkoff-ca.crt
sudo update-ca-certificates
```

Проверить настройку, не поднимая сервер:

```bash
python -m app.screener check            # токен принят, идут ли сделки по SBER
python -m app.screener universe         # пересобрать топ-N и показать обороты
python -m app.screener cycle            # один проход сбора
python -m app.screener metrics --window 60
```

### Что собирается

- Универсум — топ-N акций MOEX по среднему дневному обороту (по умолчанию
  N=100, секция `TQBR`). Оборот считается по дневным свечам, поэтому универсум
  сам обновляется раз в 12 часов (кнопка «Универсум» — пересобрать вручную).
- Лента сделок опрашивается каждые 30 секунд в торговые часы: будни
  09:40–23:55 МСК и выходные торги 09:50–19:00 МСК. API отдаёт сделки только за
  последний час, поэтому опрос идёт постоянно; окна перекрываются, а дубли
  отсекает уникальный индекс `(instrument_uid, ts_ns, price, lots)`.
- Сделки хранятся `SCREENER_RETENTION_DAYS` дней (по умолчанию 10) и чистятся
  автоматически, а перед чисткой сворачиваются в **минутки** — они живут
  `SCREENER_BAR_RETENTION_DAYS` дней (по умолчанию 365).

### Хранение: отдельная база, тик + минутки

Тики лежат в **отдельном файле** `screener.db` рядом с `broker.db`, чтобы
десятки гигабайт ленты не раздували основную базу (её бэкап, rsync на сервер и
репликация в Firebase). Уже собранные сделки из `broker.db` переносятся
автоматически при первом запуске.

| Что | Объём | Хранение |
|-----|-------|----------|
| Сырые сделки (топ-100) | ~1 ГБ/день | 10 дней → 5–10 ГБ |
| Минутки (OHLC, VWAP, buy/sell, крупные) | ~10 МБ/день | 1 год → ~1–3 ГБ |

Измерено на реальных данных: 342 байта на сделку (таблица + 4 индекса).
Каждый цикл сборщик доворачивает минутки (`rollup_bars`), а перед удалением
старого тика агрегаты пересчитываются — история не теряется.

```bash
python -m app.screener stats     # размеры, число сделок/минуток, сроки хранения
python -m app.screener rollup    # принудительно свернуть накопленное в минутки
```

### Выгрузка для исследования стратегий

```bash
# месяц в Parquet с zstd (если установлен pyarrow), иначе CSV.zst / CSV.gz
python -m app.screener export --month 2026-11 --out ./export
python -m app.screener export --month 2026-11 --ticker SBER --out ./export
python -m app.screener export --month 2026-11 --source bars --out ./export
```

Формат выбирается автоматически: `parquet+zstd` (нужен `pip install pyarrow`),
иначе `csv+zstd` (пакет `zstandard` уже в зависимостях), иначе `csv+gzip`.
На реальных данных вышло **10–12 байт на сделку** — месяц топ-100 это сотни
мегабайт вместо десятков гигабайт в SQLite.

Окно в UI намеренно ограничено «с начала дня»: живая аналитика считается по
индексу `(instrument_uid, ts_ns)` и рассчитана на ≤ 1 дня. Месячные срезы —
через `export` (или запросы к `market_bar_1m`) на исследовательской машине.

### График и бэктест

Страница `/chart/<тикер>` (в навигации — «График», из скринера — клик по тикеру).

**График** — свечи из минуток (1м/5м/15м/1ч), объём, сессионная VWAP и панель
дельты (перевес покупок над продажами в ₽). Диапазоны: сегодня / 3 / 7 / 30 дней.
Рендер — TradingView Lightweight Charts, вендорен локально
(`app/static/vendor/lightweight-charts-4.2.3`, Apache-2.0), внешних CDN нет.

**Шкала в процентах** — справа от цены отдельная колонка с изменением в % от
первой свечи диапазона. Ценовая шкала TradingView остаётся на месте: проценты
рисуются своим «рейлом» по точному линейному отображению цены в пиксель
(`priceToCoordinate`), поэтому пересчитываются при зуме и скролле.

**Волатильность** — строка под графиком, пересчитывается под выбранный
интервал и диапазон:

| Метрика | Что показывает |
|---|---|
| **ATR14**, ₽ и % | средний true range за 14 баров — абсолютный риск на бар |
| **σ бара**, % | стандартное отклонение лог-доходностей бара |
| **σ час / σ день**, % | та же σ, приведённая по корню из времени (60 мин / 840 мин сессии) |
| **размах**, % и ₽ | фактический (max−min) за диапазон — без экстраполяции |

Проценты нужны для сравнения бумаг между собой (SBER 0.29 %/день и IRKT
4.7 %/день — разница в 16 раз), рубли — чтобы считать риск позиции. В скринере
для этого две колонки: «Вол. %» (σ дневная) и «ATR ₽».

### Уровни и перевес (горизонтальные объёмы)

Цена большую часть времени ходит **между уровнями**, и вопрос не «поймать шум»,
а понять, кто действует у уровня и куда вероятнее следующее движение.

**Горизонтальный профиль объёма** (market profile) строится по обезличенным
сделкам: для каждой ценовой «полки» собирается объём покупок и продаж, на
графике рисуется слева палочками, цвет — по перевесу. Крупная сделка видна как
выброс — именно по таким местам и проходят уровни.

**Зоны** выделяются из пиков профиля: сглаживание по трём полкам и порог от
92-го перцентиля (а не от максимума), чтобы один аукционный принт на десятки
миллионов не «съедал» остальные уровни. Пересекающиеся полосы склеиваются.

**Вердикт** — не «уровень = разворот», а «кто агрессор»:

* сторону задаёт **инициатор сделок** (`side` — сторона тейкера): если у уровня
  доминируют крупные покупки, этот уровень и продавят;
* уровни — **цели**: цель всегда следующий уровень за текущим, а не тот, внутри
  которого стоим;
* различаются состояния **«цена в зоне»** и **«между уровнями»** — в первом
  решает перевес внутри зоны, во втором — дельта за последние 30 минут плюс
  перевес на ближайших уровнях.

В панели под графиком: уровень, тип (поддержка/сопротивление), объём, доля
покупок, перевес крупных и расстояние до цены. Зоны рисуются пунктиром на
графике с метками `S`/`R`.

```bash
GET /api/levels/<ticker>?range=today|3d|7d|30d&buckets=80
# → profile[], zones[], support, resistance, inside, delta, verdict{direction,confidence,target}
```

> Уровни осмысленны на диапазоне от нескольких дней: за одну тихую сессию
> (SBER 0.14 % хода) профиль даёт микрозоны шириной в копейку. Для торговли
> смотрите `7d`/`30d`, а «сегодня» — для интрадей-контекста.

**Маркеры сделок** — обезличенные сделки поверх свечей: «крупные» (от порога,
по умолчанию `SCREENER_LARGE_TRADE_RUB`) или «все» (не больше 3000, берутся
крупнейшие). Подписи показываются только у 12 крупнейших принтов, иначе график
превращается в кашу. Маркеры доступны за срок хранения тика
(`SCREENER_RETENTION_DAYS`); свечи и дельта — за весь срок минуток
(`SCREENER_BAR_RETENTION_DAYS`).

**Бэктест intraday** — прогон стратегии по минуткам с исполнением «сигнал по
закрытию бара → вход по открытию следующего». Одна позиция за раз, фиксированный
номинал, комиссия с обеих сторон, внутри бара сначала проверяется стоп.

| Стратегия | Логика входа |
|---|---|
| Импульс дельты | перевес покупок/продаж за окно ≥ порога при объёме выше среднего |
| Возврат к VWAP | отклонение от VWAP на `k` сигм волатильности баров + подтверждение дельтой за окно, выход на VWAP |
| Накопление / распределение | объём выше нормы, цена стоит, дельта перевешивает |
| За крупным принтом | перевес крупных сделок на одной стороне |

Два важных свойства модели исполнения:

* **дельта окна** = `Σ(buy−sell) / Σобъём` за окно — та же величина, что «Δ %» в
  скринере (а не средняя дельта, поделённая на объём одного бара);
* **цены исполнения** приводятся к сетке цены инструмента: выход по VWAP — по
  уровню, стоп/тейк при гэпе — по цене открытия бара (стоп в худшую сторону),
  поэтому в отчёте нет «цен» вроде `294.1134`.

Порог отклонения от VWAP задаётся в сигмах (`deviation_sigma`, по умолчанию 2),
а не в процентах: у SBER отклонение от VWAP за час редко превышает 0.1 %,
у NVTK доходит до 0.25 % — фиксированный процент либо не торгует вовсе, либо
торгует только по самым волатильным бумагам.

Результат: сделки (вход/выход, причина, P&L), equity-кривая, метрики —
до комиссий, результат, доходность, винрейт, профит-фактор, мат. ожидание,
максимальная просадка, комиссии, Шарп на сделку. Входы и выходы отмечаются
на графике.

### Стратегия: покупка от уровней (только лонг)

Рабочая стратегия одна — **лонг от уровней**. Два входа, оба в покупку:

| Вход | Условие |
|---|---|
| **Разворот** | цена подошла к поддержке (касание верхней границы зоны) и закрылась обратно над её низом, агрессор покупает (дельта за окно ≥ порога) или бар явно выкуплен |
| **Продолжение** | закрытие выше сопротивления с запасом `break_margin_pct`, объём ≥ `volume_factor` от среднего, дельта ≥ порога |

Защита от мусора: зоны шире `max_zone_width_pct` (по умолчанию 0.25 %) не
участвуют — касание «полосы на весь день» ничего не говорит; между сигналами
пауза `cooldown_min`; уровни строятся **только по данным до начала торгового
дня** (прогрев `warmup_min`), иначе бэктест видит будущее.

Выходы: стоп за нижней границей зоны, цель — следующая зона сверху (не дальше
тейк-профита), ограничение по времени. Сигналы отмечаются на графике стрелкой
**«Покупка»**, список — в панели «Сигналы на покупку».

Сигналы в панели — **отдельная таблица по дате и времени**: у каждой строки есть
колонки «дата» и «время» (момент закрытия бара, на котором сигнал появился),
порядок сортировки меняется кликом по «дата» (по умолчанию — от ранних к
поздним). Столбец «вход» показывает текущий статус: **принят** — цель дальше
стопа; **отсеян** — фильтр `min_rr` не пропустил, в подсказке виден фактический
R:R. Так видно, что сигнал был, когда он появился и почему позже не торговался.
Та же таблица по всем бумагам универсума — на странице `/screener`.

```bash
GET  /api/signals/<ticker>?range=today&interval=1    # сигналы за период
POST /api/backtest/<ticker>  {"strategy":"levels_long","params":{"use_stop":0}}
```

**Без стопа для дивидендных бумаг.** Стоп выбивает из позиции на шуме, а смысл
владения дивидендной бумагой — дивиденды и восстановление цены. Для списка
тикеров стоп можно отключить целиком:

```bash
# .env — тикеры, где стоп не применяется
SCREENER_NO_STOP_TICKERS=SBER,GAZP,LKOH,ROSN,TATN,MTSS,SNGSP
```

В интерфейсе то же делает галочка **«без стопа»** (выход только по цели или
времени). Метрики при этом показывают реальную максимальную просадку — без
стопа риск никуда не исчезает, он просто не ограничен уровнем.

### Проверка эффективности стратегии

Одна бумага ничего не доказывает, поэтому есть прогон по универсуму с
разделением периода на **in-sample** (первая часть) и **out-of-sample**
(вторая) при одних и тех же параметрах — если эффект живёт только в первой
половине, это подгонка.

```bash
python -m app.backtest run SBER --strategy vwap_reversion --range today
python -m app.backtest scan --strategy vwap_reversion --top 20 --range today --fee 0.05
python -m app.backtest scan --strategy vwap_reversion --top 20 --fee 0        # без комиссий
python -m app.backtest scan --strategy vwap_reversion --param deviation_sigma=1.5
```

То же из интерфейса — кнопка **«По универсуму»** в панели бэктеста.

> **Про комиссии.** Круговая сделка при номинале 100 тыс ₽ и комиссии 0.05 %
> за сторону стоит ~100 ₽, то есть 0.1 % от позиции. На минутных барах
> типичный ход — 0.01–0.05 %, поэтому **валовая прибыль может быть
> положительной, а итог отрицательным**: комиссии съедают больше, чем даёт
> сигнал. Смотрите карточку «до комиссий» отдельно от «результата» — она
> показывает качество сигнала, а не тариф.

У стратегии «Возврат к VWAP» есть параметр **«Порог × издержки»**
(`cost_multiplier`, по умолчанию 1.5): вход разрешён, только если отклонение
от VWAP хотя бы в 1.5 раза больше круговой комиссии. Поставьте 0, чтобы
увидеть «сырой» сигнал без экономического фильтра.

Под метриками бэктеста появляется диагноз: «сделок нет», «валовой результат
≤ 0 — у сигнала нет перевеса» или «сигнал есть, но комиссии съедают больше» —
это разные проблемы и лечатся по-разному.

```bash
# API
GET  /api/chart/<ticker>?range=today|3d|7d|30d&interval=1|5|15|60
GET  /api/chart/<ticker>/markers?range=today&mode=large|all&min_value=1000000
GET  /api/chart/<ticker>/tape?range=today&limit=100
GET  /api/volatility/<ticker>?range=today&interval=1   # ATR, σ бар/час/день, размах
POST /api/backtest/<ticker>   {"strategy":"delta_momentum","params":{...},"range":"today"}
POST /api/backtest/scan       {"strategy":"vwap_reversion","top":20,"range":"today"}
```

### Метрики

| Метрика | Смысл |
|---------|-------|
| **Дельта** | Перевес покупок над продажами: `Σ покупки − Σ продажи` в ₽ и акциях |
| **Δ %** | Дельта в процентах от общего объёма (`−100%…+100%`) |
| **Крупные** | Перевес в сделках крупнее `SCREENER_LARGE_TRADE_RUB` (1 млн ₽) — «умные деньги» |
| **Оценка** | Свёртка дельты, крупных принтов, аномалии объёма и движения цены (`−100…+100`) |
| **Активность** | Оборот за период наблюдения относительно среднего дневного оборота |
| **VWAP** | Средневзвешенная по объёму цена — база для «дорого/дёшево» |
| **Тренд дельты** | Дельта во второй половине окна минус дельта в первой |

Сигналы: `Активная покупка / продажа` (перевес ≥ 35% объёма), `Крупные
покупки / продажи` (перевес ≥ 50% в крупных принтах, не меньше трёх таких
принтов), `Накопление` и `Распределение` (объём выше нормы, но цена не идёт —
крупный игрок набирает или сбрасывает позицию), `Аномальный объём`.

Сигналы не выдаются, пока оборот за окно меньше `SCREENER_MIN_SIGNAL_TURNOVER`
(по умолчанию 1 млн ₽): «100% покупок» на трёх тысячах рублей — это шум, а не
перевес покупателей.

Под основной таблицей — карточка **«Сигналы на покупку»**: все сигналы стратегии
за сегодня по бумагам универсума, отсортированные по дате и времени появления
(клик по «дата» меняет порядок). В строке видны тикер, тип входа (разворот /
пробой), уровень, цена, дельта, объём бара и статус `принят` / `отсеян`
(отсеян — цель ближе стопа, фактический R:R в подсказке). Кнопка «только
принятые» скрывает отсеянные.

Если биржа не передала направление сделки (`TRADE_DIRECTION_UNSPECIFIED`),
сторона восстанавливается правилом тика: цена выше предыдущей — покупка, ниже —
продажа. Доля таких сделок видна в детализации как «Без направления».

### API

| Endpoint | Описание |
|----------|----------|
| `GET /api/screener?window=session&min_turnover=5000000&signal=strong_buy` | Таблица метрик (`window`: `session`, `180`, `60`, `30`, `15`) |
| `GET /api/screener/<ticker>?window=60` | Детализация: метрики, дельта по минутам, лента сделок |
| `GET /api/screener/status` | Состояние сборщика |
| `POST /api/screener/refresh-universe` | Пересобрать универсум (в фоне) |

### Ограничения

- Глубина истории сделок — 1 час от API, поэтому «с начала дня» означает
  «сколько успели собрать с момента старта сборщика».
- Токен нужен только для чтения; торговые методы не используются.
- В Docker должен быть один воркер gunicorn. Если запустить два процесса,
  второй сборщик не стартует — его отсекает файловая блокировка
  `broker.db.screener.lock`.

## Репликация в Firebase Realtime Database

Проект поддерживает автоматическую репликацию `broker.db` в Firebase RTDB.

### Настройка

1. Создайте проект в [Firebase Console](https://console.firebase.google.com/)
2. **Project settings → Service accounts → Generate new private key**
3. Включите **Realtime Database** (Start in test mode)
4. Сохраните JSON-ключ как **`app/firebase-key.json`**
5. Добавьте volume для ключа в Docker: `./firebase-key.json:/app/app/firebase-key.json`

### Параметры

Настраиваются в `app/firebase_config.py`:

| Параметр | По умолчанию | Описание |
|----------|-------------|----------|
| `SERVICE_ACCOUNT_PATH` | `app/firebase-key.json` | Путь к JSON-ключу |
| `DB_PATH_IN_RTDB` | `broker_db` | Путь в RTDB |
| `SYNC_INTERVAL` | `300` (5 мин) | Интервал фоновой синхронизации |
